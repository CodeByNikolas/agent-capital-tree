# USDC x402 feasibility on Ethereum Sepolia

Research checked 2026-09-26 against the deployed Sepolia USDC proxy, verified implementation source, and current Coinbase x402 source and facilitator metadata.

## Finding

Circle’s official Ethereum Sepolia USDC at `0x1c7D4B196Cb0C7B01d743Fbc6116a902379C7238` supports EIP-3009 authorizations from contract signers. Its proxy’s read-only `implementation()` call resolves to `0xda317c1d3e835dd5f1be459006471acaa1289068`; the verified implementation is Circle `FiatTokenV2_2`. Its ABI contains the `transferWithAuthorization(...,bytes)` overload. Circle’s EIP-3009 implementation validates that byte signature through `SignatureChecker.isValidSignatureNow`, which calls ERC-1271 for contract signers. This removes the token-level blocker for a vault acting as the payer.

The existing deployed Agent Capital Tree contracts still cannot pay from their vaults through x402. `CapitalVault` has no ERC-1271 method, and its token movement is reachable only by its immutable controller. `CapitalController` and its factories bind an immutable token pair, and the controller has no payment capability or recipient-aware service-payment method. The current deployed pair remains ACT-A/ACT-B. Funding an external owner EOA with USDC does not make that balance a vault balance.

The smallest safe route is an additive vault/controller deployment with a narrow `PAY` capability, an ERC-1271 verifier that accepts only an encoded EIP-3009 authorization signed by that node’s currently authorized operator, and controller checks for current tree/ENS authority, token, per-payment amount, and validity deadline. The signature verifier must bind the supplied recipient and authorization fields to the digest that Circle asks it to validate; it must not accept a generic agent signature as a blanket vault authorization. Amount caps remain per action, while the vault’s actual USDC balance bounds total available capital.

x402’s EVM exact scheme can settle EIP-3009 directly through the USDC contract, so no x402-specific settlement contract is required for that path. A facilitator must still verify and broadcast the payment. The live `https://x402.org/facilitator/supported` response currently lists Base Sepolia (`eip155:84532`) but not Ethereum Sepolia (`eip155:11155111`). A facilitator that explicitly supports Ethereum Sepolia is therefore required. Coinbase’s x402 network documentation permits runtime registration for EVM CAIP-2 network IDs, but it also requires the facilitator to support the requested `(scheme, network)` pair.

This is an x402 integration only when the resource server returns an HTTP 402 payment requirement, the client supplies the corresponding signed x402 payment payload, and the facilitator verifies and settles that EIP-3009 authorization. Calling ordinary `USDC.transfer` is not x402.

## Evidence

- Circle’s [USDC contract address table](https://developers.circle.com/stablecoins/usdc-contract-addresses) lists `0x1c7D4B196Cb0C7B01d743Fbc6116a902379C7238` for Ethereum Sepolia. Circle’s [verified Sepolia implementation](https://sepolia.etherscan.io/address/0xda317c1d3e835dd5f1be459006471acaa1289068#code) is `FiatTokenV2_2`; the proxy’s implementation slot was read with `eth_call` on Ethereum Sepolia.
- Circle source: [`FiatTokenV2_2.sol`](https://github.com/circlefin/stablecoin-evm/blob/master/contracts/v2/FiatTokenV2_2.sol) exposes `transferWithAuthorization(...,bytes)`; [`EIP3009.sol`](https://github.com/circlefin/stablecoin-evm/blob/master/contracts/v2/EIP3009.sol) routes it through `SignatureChecker.isValidSignatureNow`; [`SignatureChecker.sol`](https://github.com/circlefin/stablecoin-evm/blob/master/contracts/util/SignatureChecker.sol) performs ERC-1271 validation for contract signers.
- Coinbase x402’s [EVM exact EIP-3009 client](https://github.com/coinbase/x402/blob/main/typescript/packages/mechanisms/evm/src/exact/client/eip3009.ts) creates the typed authorization; the [facilitator implementation](https://github.com/coinbase/x402/blob/main/typescript/packages/mechanisms/evm/src/exact/facilitator/eip3009.ts) validates the recipient, amount and time window, simulates settlement, and calls `transferWithAuthorization`.
- x402’s [network and token support](https://github.com/coinbase/x402/blob/main/docs/core-concepts/network-and-token-support.mdx) says EVM assets can use EIP-3009 and that arbitrary EVM networks can be registered at runtime if the facilitator supports them. The current [hosted facilitator capabilities endpoint](https://x402.org/facilitator/supported) does not include Ethereum Sepolia.
- The x402 [Permit2 proxy deployment table](https://github.com/coinbase/x402/blob/main/contracts/evm/README.md#current-deployments) currently documents Base and Base Sepolia deployments only. That proxy is unnecessary for Circle USDC’s EIP-3009 path.
- Local implementation facts: [`CapitalVault.sol`](../contracts/src/CapitalVault.sol) makes token transfers controller-only and implements no ERC-1271 interface; [`CapitalController.sol`](../contracts/src/CapitalController.sol), [`VaultFactory.sol`](../contracts/src/VaultFactory.sol), and [`NodeFactory.sol`](../contracts/src/NodeFactory.sol) bind the token pair at deployment. [`FinanceRoles.sol`](../contracts/src/ens/FinanceRoles.sol) currently has no payment role.

## Deployment consequence

The current vault and controller addresses are immutable deployments. Adding EIP-3009/ERC-1271 behavior and the PAY policy path requires new vault bytecode and a new controller/factory stack; it cannot be attached to existing vaults by funding or by changing the frontend. The existing tree and its ENS namespace should remain untouched. A parallel tree needs a distinct registered ENS namespace because the current controller verifies that its namespace points to its own immutable `PROJECT_REGISTRY`. If the new tree uses the current pool-oriented controller, its configured pair must include official USDC and a second compatible token; a USDC-only payment deployment can be smaller if implemented as a purpose-built payment controller and vault rather than carrying unused swap/LP infrastructure.

The operator-confirmed 20 USDC transfer to the test owner EOA is suitable funding for that EOA, not for an existing tree vault. It does not alter this deployment requirement.
